Веб-приложение с двумя списками: слева - все невыбранные ID, справа - выбранные.
Состояние выбора и порядка общее для всех пользователей.

Стек: **Express.js** (бэкенд), **React + TypeScript + Vite** (фронтенд), **PostgreSQL**, **RabbitMQ**, **Redis**, **Socket.IO**.

## Что сделано по заданию

| Требование | Реализация |
|---|---|
| 1 000 000 элементов, ID 1…1 000 000 | Сид миграцией `generate_series(1, 1000000)` |
| Два окна: слева невыбранные, справа выбранные | `LeftPanel` / `RightPanel` |
| Фильтр по ID в обоих окнах | Префикс по строке ID (`LIKE '123%'`), не более 9 цифр |
| Infinite scroll, порции по 20 | Cursor-пагинация, `MAX_LIMIT=20`, sentinel + `IntersectionObserver` |
| Добавление элемента с произвольным ID | Форма слева - `POST /api/v1/item` |
| Drag & Drop сортировка справа, в том числе по отфильтрованному списку | `@dnd-kit`; новый `sortWeight` считается относительно соседей в текущем (в т.ч. отфильтрованном) списке |
| Перенос между окнами | Drag слева-справа / справа-слева, клик по строке слева, кнопка «×» справа |
| Сохранение выбора и сортировки между обновлениями страницы | Хранится на сервере; поиск в сохранённый порядок не входит |
| Поиск не сохраняется как часть состояния выбора | Поле поиска не пишется в таблицу `items` |
| Без учёток, данные общие | Один набор записей на всех |
| Очередь + дедупликация, один ID не добавляется повторно | RabbitMQ + `DeduplicatedBatchBuffer` по `id`; `INSERT … ON CONFLICT DO NOTHING`; на API - 409, если ID уже есть |
| Батч добавления раз в 10 с | `AddBuffer`, интервал 10 000 мс |
| Батч получения/изменения раз в 1 с | `SelectBuffer` и `ReorderBuffer`, интервал 1 000 мс |
| Express.js | HTTP API + Socket.IO на том же процессе |

Дополнительно (чтобы миллион строк и несколько клиентов работали предсказуемо):

- cursor-пагинация и частичные индексы под оба списка и под префиксный поиск;
- ревизии состояния (`state_revision`) - клиент отбрасывает устаревшие WS/HTTP ответы;
- live-обновление всех вкладок через Socket.IO после каждого flush батча;
- optimistic UI: выбор/снятие выбора сразу на клиенте, затем подтверждение с сервера.

## Как устроено

```
Клиент (React)
  HTTP  POST add / select / reorder  -  Express (202 Accepted)
  HTTP  GET  /item, /item/selected, /item/state  -  страница по 20
  WS    items:added | selection-changed | reordered

Express
  - RabbitMQ  add.queue | select.queue | reorder.queue
  - DeduplicatedBatchBuffer (ключ = id, последнее значение побеждает)
  - flush: INSERT/UPDATE батчем в PostgreSQL, bump revision
  - Socket.IO emit всем клиентам
```

Мутации **не пишут в БД из HTTP-хендлера**.
Хендлер валидирует DTO, публикует сообщение и отвечает `202`.
Фактическая запись - в consumer после батча.

### Дедупликация

1. **В буфере.** `Map` по `id`: повторное сообщение с тем же ключом заменяет payload, ack копится. В один flush попадает одно значение на ID.
2. **В БД при add.** `INSERT … ON CONFLICT (id) DO NOTHING` - повтор не создаёт вторую строку.
3. **На входе API.** `existsById` - `409 Conflict`, если ID уже есть.
4. **На клиенте.** Списки склеиваются с дедупом по ID.

Некорректные сообщения из очереди уходят в nack без requeue, чтобы не крутить мусор.

### Пагинация и поиск

- Слева курсор - последний `id` страницы, сортировка по `id`.
- Справа курсор - `sort_weight` последнего элемента, сортировка по `sort_weight`, затем `id`.
- Поиск - префикс `id::text LIKE $search%`. При поиске лимит тот же: 20, дальше - скролл.
- `GET /api/v1/item/state` отдаёт первую страницу обоих списков в одной транзакции `REPEATABLE READ`, чтобы bootstrap не разъехался.

### Реалтайм

После flush:

- `items:added` - новые ID;
- `items:selection-changed` - выбранные (с весами) и снятые;
- `items:reordered` - обновлённые веса.

Клиент применяет событие, только если `revision` не старше текущего.

## Модель данных

`items`

| Поле | Смысл |
|---|---|
| `id` | PK |
| `is_selected` | в правом списке |
| `sort_weight` | порядок среди выбранных |
| `selected_at` | момент выбора |
| `created_at` | момент появления |

`state_revision` - монотонный счётчик, увеличивается на каждый успешный flush.

Индексы: невыбранные по `id`, выбранные по `(sort_weight, id)`, префиксный поиск по `id::text` отдельно для каждой стороны.

В ТЗ достаточно in-memory на время жизни процесса, но я решил использовать PostgreSQL: миллион строк, пагинация и общий state переживают рестарт контейнера.
Очередь и батчи - как требовалось.
